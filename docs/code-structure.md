# コード構成と変更時の注意

## 画面と部品

- index.html: 公開資料の内容。作品・価格・写真・イベントの正本照合はここから開始
- board.js: ボードのナビ、コメントの投稿・編集・対象別表示。以前の対象名は保存済みコメントとのキーになるため、表示名の訂正時も保全
- board.css: 従来の基本デザイン。studio.css: スマホと4分類のレイアウト。typography.css: 書体と読みやすさ
- ui-core.js: 画面部品の生成、安全な保存ID、差分だけのdisabled更新。通信・保存・認証判断を持たせない
- ime.js: ネイティブIMEの変換状態だけをメモリ管理。入力値・選択範囲・フォーカスを書き換えない
- context-comments.js: 記録/出店への対象別コメント。private.js: 記録の一覧/編集/金額集計。event.js: 出店ごとの準備と選択

## 認証と保存

`comment-coverage.js` は全コーナーの固定IDと共通エディターの登録・監査を担当。写真一枚ずつを含め、個々の情報には必ずコメント導線を設ける。新規コーナーの追加時は [全コーナーのコメント実装規則](comment-corners.md) と `npm run check:comments` を使用。既存の保存キーを変更せず、Dotのカスタム指示は変更しない。

comments-api.jsがLINE認証を開始し、Workerのsession応答で確認されたviewerを画面へ通知。各画面は認証済みの間だけ非公開データを表示。背景移行/認証拒否では即座に消し、同じviewerの再確認後だけメモリの下書きを復元。表示名は下書きの識別に使わない。

backend/worker.jsはリクエストごとにLINEの検証APIと二名の許可リストを確認。records.jsとevents.jsは各保存形式・版競合・履歴保全を担当。認証やDBスキーマの変更は単なる見た目の修正と分けて確認。本人限定テストは独立した入口・DB・許可条件を保持。

## 更新の手順

1. 元の対象ID・旧コメントキー・写真・価格条件を確認
2. 必要な機能のモジュールを編集。入力イベント内でtextareaの属性や値、周辺ラベルを再描画しない
3. npm run format、npm test、npm run check、npm run privacy、npm run format:checkを実行
4. 公開差分に秘密・私的な本文・金額・新しい未承認写真がないことを確認
5. 公開後は配信ファイルと未認証拒否を確認。実LINEのIME確認は自動テストとは区別

公開資産の一覧はscripts/public-assets.jsonへ集約。owner-testビルドも同じ一覧を使う。comments-config.jsは本番とテストで別々に生成/管理し、誤って保存先を混ぜない。

## 書体

Zen Maru GothicのMedium/BoldをOFLライセンス付きで自前配信。font-display:optionalで初期表示後の急な書体切替を避け、未読込時は端末フォントを使う。初回の低速通信ではフォールバックのまま表示し、次の表示で読み込まれた書体を使う。画像・トークン・記録を外部フォントサービスへ送らない。
`comment-state.js` はコメントの未対応／対応済み表示と明示的な状態変更を共通化。本文へ印を埋め込まず、APIの状態と版番号を使用。新規入力欄を再生成せず、編集中の本文がある場合は状態変更を待つ。サーバー側の本文編集は投稿者だけ、対応状態は二人で共有。本文の再編集で未対応へ戻す。
